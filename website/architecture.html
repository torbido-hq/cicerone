Architecture

How the packages under src/cicerone/ fit together. Batch training stays out of the serve and dashboard request paths.

Core loop

  1. Input — io backends (dataset or db) load events, users, and items.
  2. Dataset — weighted interactions become a rectools BuiltDataset; policies keep user/item frames.
  3. Model — strategies fit and recommend; combiners merge by priority or weighted RRF.
  4. Output — top-K rows (and optional artifacts / items snapshot) written to the configured sink.
  5. Schedule — in-process cron, plus optional retrain webhook / input poll behind a debounce lock.

Package map

AreaResponsibility
config/Load and validate TOML; nested serve/trigger/dashboard/AutoML settings
io/InputSource / OutputSink / recommendation & manifest readers
model/Strategy registry, fit workers, recommend, combine
job.py · scheduler.pyOne end-to-end run; cron + trigger hosting
serve/FastAPI read API + Prometheus helpers (no ML imports)
dashboard.pyStandalone status UI (Jinja + htmx)
automl.py · policy.pyBacktests; eligibility masks and boosts
artifact.pyOptional versioned fitted-model bundle

Serve vs batch

python -m cicerone.serve never loads LightFM, rectools, or implicit. It refreshes a lookup table (dataset cache or DB query) and returns precomputed rows — cold-start falls back to the __cold_start__ ranking when a user is missing.

The dashboard similarly reads manifests only. Both keep ML out of the hot path so you can scale read replicas without shipping the training stack.

I/O backends

Input and output are independent. dataset uses parquet on local disk or S3-compatible storage; db uses SQLAlchemy tables. Compose profile db brings up Postgres for local exercises; CI uses a throwaway instance via docker-compose.ci.yml.
